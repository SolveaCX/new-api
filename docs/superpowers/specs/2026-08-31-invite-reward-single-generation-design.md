# 邀请奖励单代来源约束设计

- 日期：2026-08-31
- 状态：已确认方案，待实施计划
- 分支：`fix/invite-reward-provenance`

## 1. 背景与目标

订阅邀请模式允许邀请抵扣把订单应付金额降到 0。这个行为本身是合法产品能力，不能因为订单为 0 元就拒绝开通套餐。

当前问题是：订单成功后，奖励发放只检查 `status=success`，而抵扣账本在 `reserve/commit` 后没有保留原始 grant 来源。于是由 `grant_inviter` 额度支付的订单也会再次给上游邀请人发奖励，形成“奖励支付 → 再发奖励”的套娃链。

本设计的目标：

1. 0 元订单仍可以按正常状态机开通或续费。
2. 每笔订单的邀请奖励只发给该订单用户的直接邀请人，不沿邀请树向上递归。
3. 使用邀请人奖励（`grant_inviter`）或来源无法证明为非邀请人奖励的抵扣订单，不再铸造新的上游邀请奖励。
4. 注册新人抵扣、普通优惠或自身余额产生的 0 元订单，仍可按一级规则给直接邀请人发一次奖励。
5. 不因阻止上游奖励而回滚订单开通、受邀人抵扣或已完成的支付状态。

## 2. 非目标

- 本次不自动撤销历史 Pro 权益、不追缴已消耗额度，也不删除历史账本。
- 不禁止被邀请用户继续邀请好友；禁止的是奖励来源的递归再生。
- 不以 `payment_amount_minor > 0` 作为唯一门槛；合法的 0 元订单必须保留。
- 不改变注册新人优惠的金额、有效期或套餐适用范围。

## 3. 领域规则

### 3.1 抵扣来源枚举

为订阅抵扣预占和终态流水增加来源标记：

| 来源 | 含义 | 是否允许产生直接邀请奖励 |
| --- | --- | --- |
| `none` | 本单未使用订阅抵扣 | 允许 |
| `invitee` | 仅使用注册受邀人抵扣或其他非邀请人来源 | 允许 |
| `inviter` | 使用了邀请人奖励额度 | 禁止 |
| `mixed` | 同时存在或无法拆分多种来源，可能包含邀请人奖励 | 禁止 |
| `unknown` | 历史记录缺少来源或调用方未提供来源 | 禁止（仅阻止新奖励） |

来源标记只影响“是否给上游发奖励”，不影响本单套餐权益。

### 3.2 一次订单的奖励行为

奖励发放入口继续保持现有的受邀人幂等键（每个受邀人最多一条奖励记录），并且只读取受邀人的直接 `inviter_id`。在创建奖励前：

1. 若订单没有订阅抵扣，按现有一级规则发给直接邀请人。
2. 若订单抵扣来源为 `invitee`，即使最终应付为 0，也按现有一级规则发给直接邀请人。
3. 若来源为 `inviter`、`mixed` 或 `unknown`，创建一条 `blocked` 奖励记录并记录原因，不创建正向抵扣流水；订单和受邀人侧状态保持成功。

“不明来源拒绝发奖”是安全上的 fail-closed 选择，避免旧数据或并发路径再次铸造奖励；它可能使少量历史奖励需要人工复核，但不会影响用户已经获得的套餐。

## 4. 数据流与组件

### 4.1 账本来源持久化

在 `SubscriptionDiscountEntry` 增加 `funding_source` 字段，并在 `SubscriptionDiscountReservationInput` 中传递来源。预占行写入来源；`commit`、`release` 终态行复制预占行来源，保证重试、对账和异步回调不会丢失信息。

现有的 `PricingSnapshot` 同步写入来源，便于订单审计和旧数据排查。字段使用白名单枚举并由后端校验，不能由前端报价值直接决定。

### 4.2 来源解析

预占发生在数据库事务内并锁定抵扣账户。解析器按以下原则返回来源：

- 没有抵扣金额时返回 `none`。
- 账户历史中没有正向 `grant_inviter` 额度时，返回 `invitee`。
- 存在可用或无法排除已进入本次抵扣的 `grant_inviter` 额度时，返回 `inviter` 或 `mixed`。
- 历史流水不完整、迁移来源无法判定、或调用方未能提供可信来源时，返回 `unknown`。

混合来源采用保守拒绝策略，不尝试在没有批次/lot 记录的旧账本上猜测消费顺序。

新建预占在可证明的情况下采用固定优先级：先消耗注册受邀人额度，只有请求金额跨入邀请人额度时才标记为 `mixed`。这样同一账户中恰好同时存在两类余额时，仍能保留明确的受邀人首订优惠；旧记录无法证明消费批次时继续按 `unknown` 处理。

### 4.3 奖励发放

`TryGrantInviteSubscriptionRewardAfterOrderCompleted` 在现有成功状态检查后，读取订单的抵扣预占来源（必要时使用兼容回退解析）。只有 `none` 或 `invitee` 进入现有 `grant_inviter` 流程；其余来源走阻断记录流程。阻断流程必须：

- 使用受邀人幂等键，避免重试重复写入；
- 不增加邀请人的抵扣账户余额、不增加邀请统计；
- 完成受邀人的奖励状态收尾，保留订单审计事实；
- 输出可检索的阻断原因和订单号。

### 4.4 覆盖的订单路径

同一来源规则覆盖：

- 余额购买（包括应付 0 元）；
- Stripe/其他支付回调完成；
- 续费发票抵扣和重试；
- 奖励补偿/历史扫描任务。

任何路径都不得仅因为 `Money=0` 或 `PaymentAmountMinor=0` 而撤销套餐；只在奖励层阻止递归发放。

## 5. 兼容与迁移

- 使用 GORM `AutoMigrate` 增加非破坏性字段，默认值为 `unknown`。
- 旧的预占/终态流水没有来源时按 `unknown` 处理；补偿扫描不会为其新增上游奖励，除非能证明来源为 `none`/`invitee`。
- 不回写或删除历史正向奖励，不在本次变更中做权益追回。
- 新旧节点短期并行时，旧节点可能仍写入无来源流水；发布顺序应先部署兼容字段和读取逻辑，再切换所有生产节点，最后观察阻断指标。

## 6. 测试与验收

必须先添加失败测试，再实现：

1. 注册受邀人抵扣把订单降为 0 元时，直接邀请人仍获得一次奖励。
2. `grant_inviter` 来源抵扣把订单降为 0 元时，套餐成功、上游奖励为 `blocked`，且没有新增抵扣流水。
3. 混合/不明来源时同样只阻止上游奖励，不影响套餐开通。
4. 未使用订阅抵扣、由自身余额支付的订单仍按一级规则发奖。
5. 预占、提交、释放和重复回调都保留来源并保持幂等。
6. 余额、外部支付、续费和补偿扫描路径共享相同判定结果。
7. 并发订单不会绕过来源判定或生成两条奖励。

验收标准：不存在由 `grant_inviter` 来源订单产生的正向 `grant_inviter` 流水；合法 0 元 `invitee` 来源订单仍能完成套餐和一级奖励；所有既有订阅生命周期测试保持通过。

## 7. 风险与观测

来源不明的订单会少发奖励，需要在管理后台/日志中按 `inviter_reward_reentry`（或等价原因）统计并支持人工复核。发布后应持续监控：阻断奖励数量、0 元订单数量、抵扣来源未知数量，以及奖励流水与订单的关联完整性。
